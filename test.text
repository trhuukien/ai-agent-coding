# AI Support Theme — CLAUDE.md

## Project Overview
AI agent that takes natural language requests from customers and applies changes to a Shopify theme.
The agent uses 3 tools: `list_theme_files`, `read_theme_file`, `write_theme_file`.
After writing files locally, they are pushed to Shopify via CLI.

## Figma Integration (workflow-e.js)

`fetch_figma_node(url)` tool (in `shared.js`) fetches a Figma frame/node via the Figma REST API
(`FIGMA_ACCESS_TOKEN` in `.env`) and returns exact `characters`/`font`/`color` (hex)/`box`/`padding`
data — use this instead of estimating values from a screenshot whenever the task/description
contains a figma.com link. See `src/figma/fetch-figma.js`.

**Known behaviors/gotchas (already handled by the tool, described here so you don't re-derive them):**
- Hidden Figma layers (`visible: false`) are filtered out at every depth, including inside a
  requested root's own children — a layer toggled off in Figma never appears in the output.
- A TEXT node's own `font`/`color` only reflects its *base* style. When part of the text is
  styled differently (a "highlight" — different color/italic/weight on a phrase), that shows up as
  a `mixedStyleRuns` array on the node instead: one entry per contiguous run, each with `text` plus
  whatever of `fontFamily`/`fontWeight`/`italic`/`color` differs from the base. No array = uniform
  text, nothing to highlight. When mapping a highlighted run into a section/block's heading string,
  wrap the run's `text` in `[...]` per the bracket-highlight convention below, and set
  `highlight_type` (only if that schema exposes it) to `font_highlight` for a color/italic/font
  change, or `underline` for a plain underline.
- Every top-level section frame in a Figma page is the same width as the artboard (e.g. 1920px) —
  that's just Figma's page layout, NOT evidence a section should be `full_width`. Determine
  `full_width`/`make_full_page_width` by comparing the section's real content children (check one
  level deeper if the first child is itself just a padding wrapper) against the frame width: ~0-30px
  gutter on both sides → genuinely full width; ~250-270px gutter (on a 1920px artboard, matching the
  theme's normal `page_width`) → leave at the schema default. When the gutter is the small ~20-30px
  kind (full width, but not 0px), check the section's schema for a companion toggle — several
  sections in this theme (`multicolumn.liquid`, `social-feeds.liquid`) name it `padding_full_width`
  ("Enable side padding") — that must ALSO be set true, or `full_width` alone renders fully
  edge-to-edge (0px gutter) instead of the small side padding the design shows. Not every
  `full_width` section has this toggle — some (`collection-list.liquid`, `video-looping.liquid`)
  already hardcode the small gutter whenever `full_width` is on, with no separate setting needed —
  so read the section's own `{% liquid %}` class-assignment block near the top of the file to see
  which behavior applies before deciding.
- Before writing a template JSON, explicitly clear (`""`, not omit) any optional text/richtext
  setting whose schema `default` is non-empty placeholder copy (e.g. "Example subheading", "Column")
  if the design doesn't show that content — an omitted key still renders the schema default, and
  templates almost always guard on `!= blank`, so a non-empty default renders as if it were real.

1. `list_theme_files` → understand structure
2. `read_theme_file` → read before editing

- For style changes: prefer `assets/custom.css`
- For section config: edit the relevant `.liquid` or `templates/*.json`

## Shopify Theme Structure
```
assets/          → CSS, JS, images
blocks/          → Block components (.liquid)
config/          → settings_schema.json, settings_data.json (global theme settings)
layout/          → theme.liquid, password.liquid
sections/        → Section files (.liquid) — define schema + markup
snippets/        → Reusable partials (render 'snippet-name')
templates/       → Page templates (.json for OS 2.0, .liquid for legacy)
locales/         → Translation strings
```

---

## Shopify OS 2.0 Template JSON (CRITICAL)

Templates like `templates/product.json` define sections and blocks for each page.

**Structure:**
```json
{
  "sections": {
    "main": {                          ← section key (= section ID for CSS scoping)
      "type": "product-information",  ← maps to sections/product-information.liquid
      "blocks": {
        "product-details": {          ← static block key
          "type": "_product-details",
          "static": true,
          "blocks": {
            "text_aEtTtq": {          ← nested block key
              "type": "text",
              "settings": { ... }
            }
          }
        }
      },
      "settings": { ... }
    }
  }
}
```

---

## custom_css (CRITICAL — common mistakes)

**Format:** Array of strings, NOT a plain string.

```json
"settings": {
  "custom_css": [
    ".selector { property: value; }"
  ]
}
```

`custom_css` is a **Shopify platform-native feature** in OS 2.0 — no liquid code needed to render it. Shopify automatically outputs it as a scoped `<style>` tag for the section.

---

## Block IDs & CSS Selectors (CRITICAL)

In `snippets/text.liquid`, blocks render with class:
```
text-block text-block--{{ block.id }} {{ block_settings.type_preset }}
```

**`block.id` in rendered HTML is NOT the JSON key.**
Shopify generates a compound ID: `{shopifyGeneratedPrefix}__{jsonKey}`

Example:
- JSON key: `text_aEtTtq`
- Rendered `block.id`: `AdWUyaloxN0U5RkJqb__text_aEtTtq`
- CSS selector: `.text-block--AdWUyaloxN0U5RkJqb__text_aEtTtq`

**The prefix (`AdWUyaloxN0U5RkJqb`) is NOT in any local file.** It is generated by Shopify's runtime and only discoverable via:
1. Rendered HTML (DevTools or Storefront fetch — but store may be password protected)
2. Shopify Admin API (theme files endpoint)
3. Theme editor UI → Custom CSS panel (shows correct selector automatically)

**Do NOT guess the selector from JSON keys alone.** Use `fetch_rendered_html` tool (when available) or ask the user to check the theme editor Custom CSS panel.

## Section Settings vs Block Settings

- **Section settings** → stored in `templates/*.json` under `"sections" > "sectionKey" > "settings"`
- **Block settings** → stored under `"sections" > "sectionKey" > "blocks" > "blockKey" > "settings"`
- **Global theme settings** → stored in `config/settings_data.json`

## CSS Override Strategy

**Priority order (safest first):**
1. `custom_css` in section settings (`templates/product.json`) — scoped to section, no file creation needed
2. `assets/custom.css` — global, works for any selector, requires knowing exact class
3. Edit `{% stylesheet %}` block inside section `.liquid` — works but modifies theme files

For option 1, always use array format and ensure you have the correct rendered selector.
For option 2, use when selector is known or when change is global.
